# AgentJobs 风险分析与缓解策略 - 市场验证（验证期 2026-10-25 ~ 11-22）

> **阈值引用规则**：本文档**不定义任何验证阈值**。所有验证判定一律引用 `validation-metrics.md` 的「判定阶梯」指标编号（M1–M12、S1–S3、D1–D2）。此前本文档自行维护的一套「成功指标」与 `validation-metrics.md` 的「最小成功标准」冲突：同一项目可在一份文档判定为验证通过、在另一份判定为三项关键风险全部失败。该并行标准已废止。

## 产品风险评估

### 风险 1: 需求风险 (Market Demand Risk)
**风险描述**: AI Agent 开发者市场可能不够成熟或规模不足，无法支撑一个专门的求职平台。

**风险等级**: 高

**验证方法**:
- 创建着陆页，测量访问量和邮件订阅转化率
- 发布问卷，了解AI Agent开发者的真实求职需求
- 进行10次开发者访谈，验证他们的求职痛点

**判定标准**（引用 `validation-metrics.md` 判定阶梯）：
- 通过：M1 ≥ 50（首周）、S3 ≥ 100、M4 ≥ 60%、M5 ≥ 70%
- 失败：命中 M1 < 10（首周）或 S3 < 50 或 M4 < 20% 或 M5 < 50% 任一

**缓解策略**:
- 从小众社区开始验证 (如 LangChain、AutoGen 用户群)
- 如果 AI Agent 开发者市场过小，考虑扩展到更广泛的 AI/LLM 开发者
- 探索其他 AI 相关职位类别作为补充

### 风险 2: 供给风险 (Talent Pool Risk) 
**风险描述**: 企业雇主可能还不充分理解 AI Agent 开发的需求，难以提供足够的高质量职位。

**风险等级**: 高

**验证方法**:
- 联系 5 家 AI 公司，了解他们的 Agent 招聘需求
- 分析现有求职平台上 AI/ML 职位的数量和质量
- 研究 AI Agent 初创公司的融资和发展情况

**判定标准**（引用 `validation-metrics.md` 判定阶梯，企业侧分母为 S2 = 5 家完成访谈）：
- 通过：S2 ≥ 5、M6 ≥ 40%、M8 ≥ 20%（≥ 1 家承诺发布）、M9 ≥ 60%
- 理想：M6 ≥ 70%、M8 ≥ 40%（≥ 2 家）
- 失败：S2 < 2 或 M6 < 10% 或 M8 = 0 家或 M9 < 30%

> 历史修正：本文档旧版要求"至少 3 家企业承诺发布职位"，而 `validation-metrics.md` 旧版要求"≥ 20% 受访企业承诺试用"（基数为 5 时仅 1 家）。同一指标两个门槛。现统一采用 M8 的百分比口径，并在 S2 = 5 的基数下等值为"通过 ≥ 1 家 / 理想 ≥ 2 家"。

**缓解策略**:
- 早期专注于 AI Agent 初创公司和大型科技公司的 Agent 实验室
- 提供教育内容帮助企业理解 AI Agent 开发需求
- 如果职位供给不足，考虑先构建人才池再接触企业

### 风险 3: 差异化风险 (Differentiation Risk)
**风险描述**: 无法与现有求职平台形成明显差异，AI Agent 开发者选择使用通用平台。

**风险等级**: 高（2026-10-25 由「中高」上调）

**验证方法**:
- 对比现有求职平台的 AI/ML 职位搜索体验
- 询问开发者对当前求职平台的不满之处
- 分析技术专用求职平台的优缺点
- **（2026-10-25 新增）** 对比已在运营的 Agent 垂直竞品，而非仅对比通用平台

**判定标准**（引用 `validation-metrics.md` 判定阶梯）：
- 通过：M10 ≤ 5/10、M11 ≥ 70%、D1 ≥ 3 个
- 理想：M10 ≤ 4/10、M11 ≥ 90%、D1 ≥ 5 个
- 失败：D1 = 0 个，或 M10 ≥ 7/10，或 M11 < 40%

> 历史修正：本文档旧版将"找到 3 个以上差异化功能点"定为成功指标、"找不到 3 个以上"定为差异化验证失败；而 `validation-metrics.md` 旧版的最小成功标准只要 2 个。判定阶梯统一为 D1 通过值 ≥ 3 个、失败值 = 0 个。

#### ⚠️ 2026-10-25 更新：垂直竞品已存在，本风险的性质已改变

任务 18 [A3.1] 的公开资料检索（产出见 `validation/schemas/competitors-research.md`）发现：
**「市场上缺乏专门平台」这一前提不成立——已有至少两个在运营的 Agent 垂直招聘平台。**

| 竞品 | 官方页自述规模 | 关键特征 | 来源 |
|---|---|---|---|
| `agenticcareers.co` | **2,962 岗位 / 890 家公司**，23 个方向分类，索引日更 | 含 "agentic AI engineer" 453 个岗位；提供远程 / 级别 / 地区 / 薪资筛选 | https://agenticcareers.co/state-of-agentic-hiring |
| `agenticengineeringjobs.com` | **200 个 agentic 岗位** | 按角色分类（AgentOps Engineer 44 / Prompt Engineer 85 / LLM Engineer 20 等），支持 "Post a job" | https://agenticengineeringjobs.com/llm-info |

**对本风险的三点影响**：

1. **D1 的参照系必须更新。** D1（明确差异化功能点数 ≥ 3）此前隐含参照物是**通用平台**
   （LinkedIn / Indeed / Glassdoor）。但「技能标签 + Agent 岗位专区」这类相对通用平台的差异化，
   **垂直竞品已经提供**——它们做得更细（如 agentic 专属岗位分面、AgentOps/Prompt/Agent Architect
   角色分类）。继续按原参照系计点，会得出「差异化已成立」的错误结论。
   D1 的差异化点须改为**相对 `agenticcareers.co` / `agenticengineeringjobs.com` 计量**。
2. **品牌与域名存在冲突。** `agentjobs.com` 已被一个同名招聘板占用，
   定位表述为 "Agentic AI Jobs for Builders" / "The jobboard for the new AI workforce"，
   当前为 "launching soon" 占位页（© 2026 AgentJobs.com）；`agentjobs.io` 为 Sedo 停放域名。
   与本项目的 "AgentJobs" / "The job board for people who build AI Agents" 在**品牌名与 slogan 上高度重合**。
   上线前必须解决命名（替代名或不同主域名），否则存在商标与域名纠纷风险，
   且着陆页投放文案会与占位方撞车。
3. **`requirements.md` 的核心假设已被公开资料证伪。** 该文档写「市场上缺乏一个专门为 AI Agent
   开发者提供职业机会的专业化平台」——现有证据与之冲突。
   **本节不直接改写 `requirements.md`**：假设的修正须结合访谈与问卷证据，
   属任务 8 [H4.1]（基于访谈与问卷更新产品定义）的范围，且须由创始人确认。
   但**该冲突必须在第 4 周判定前解决**，否则验证结束时会在一个已被证伪的假设上做决策。

**风险等级由「中高」上调为「高」**：竞争者已存在且规模可观（2,962 岗位 / 890 家公司），
风险 4（冷启动）的难度随之显著上升——新平台面对的是一个已有供给的存量市场。

**缓解策略（2026-10-25 修订，2026-10-31 合并）**:
- 差异化点重新锚定到**垂直竞品尚未覆盖的缝隙**（待任务 19 [A3.2] 的结构化对比表与任务 6/7 的实操确认）
- 差异化叙事须能回答「为什么不直接用 agenticcareers.co」
- 命名与域名冲突须在上线前解决（品牌风险，非仅运营风险）
- 构建 AI Agent 开发者的专属社区功能
- 提供行业趋势和薪酬洞察等增值服务

> **已废止（2026-10-25）**：「强调技能标签和技术栈匹配功能」不再是差异化点——垂直竞品已提供且粒度更细（见上方「对本风险的三点影响」第 1 条与 `validation-metrics.md` D1 条目的基准变更）。若继续把它当作差异化卖点，等于向已被竞品覆盖的功能投入，并会抬高 D1 的失真风险。
>
> 上述五条缓解策略的**执行时点已因窗口顺延而调整**：任务 19 [A3.2] 落在第 3 周（11-08 ~ 11-14），命名冲突的解决须在**第 2 周着陆页上线前**完成——否则推广文案会与占位方撞车。

### 风险 4: 双边市场冷启动风险 (Cold-Start Risk) 🔴

**风险描述**: AgentJobs 是双边市场。求职者因没有职位而不来，企业因没有求职者而不发布职位，两个循环互为前提、均无法自行启动。旧版风险台账未包含此项，但它是本项目最可能的失败模式——**范围控制无法缓解冷启动，只有供给侧的预先 seeding 可以**。

**风险等级**: 高

**为什么这是独立于风险 1/2 的风险**: 风险 1 问"需求是否存在"，风险 2 问"供给是否存在"，风险 4 问"**即使两侧需求都存在，双方能否在同一时点互相找到**"。前两者可通过访谈与意向调查验证；后者只能通过**真实交易**验证。

**验证方法**:
- 争取 M8 承诺的企业在平台上线前**预置真实职位**（作为 seed 供给），而非仅承诺"以后会发"
- 追踪 D2 成功职位匹配数（面试或入职）——这是唯一的终端证据指标
- 观察职位详情页的浏览量与投递转化率，判断供给侧种子是否真的吸引了需求侧

**判定标准**（引用 `validation-metrics.md` 判定阶梯）：
- 通过：D2 ≥ 1（达成至少 1 个真实匹配）
- 失败：D2 = 0 且 M1–M12 中 ≥ 3 项落在未达标区间

**缓解策略**:
- **预先 seeding**：平台开放前，先用 M8 承诺企业的真实职位填充，使需求侧首次访问即有内容
- **单边突破**：若 30 天内供给无法 seeding，改为先只服务开发者侧（免费职位聚合），把企业侧延后
- **人工撮合兜底**：早期匹配由创始人手动撮合，不依赖平台算法，以此绕过冷启动
- **降低启动门槛**：接受"非 Agent 岗位"作为早期供给填充，明确标记为占位，避免空平台第一印象

> 旧版 `requirements.md` 要求"第一个月至少 10 个企业发布职位"并"至少达成 1 个成功职位匹配"，但未定义这 10 家企业的获取路径——访谈（M8 承诺）不构成投放渠道。此缺口由本风险的 seeding 策略补齐。

## 其他次要风险

### 风险 5: 技术风险 (Technology Risk)
**风险描述**: AI Agent技术栈变化快，可能导致平台定位过时。

**风险等级**: 中

**缓解策略**:
- 保持平台的灵活性，易于添加新的技能标签
- 与AI Agent开发社区保持紧密联系
- 关注技术趋势，及时调整平台功能

### 风险 6: 运营风险 (Operational Risk)
**风险描述**: 作为Solo Founder项目，可能难以维持平台的日常运营。

**风险等级**: 中

**缓解策略**:
- 设计自动化程度高的运营流程
- 优先考虑低维护的商业模式
- 考虑社区驱动的内容审核和管理

### 风险 7: 竞争风险 (Competition Risk)
**风险描述**: 大型求职平台可能推出AI Agent相关功能。

**风险等级**: 高（2026-10-25 由「中」上调）

**判定标准**: 不设独立阈值，由 D1 承载——若差异化功能点无法累积到 D1 通过值 3 个，说明差异化壁垒不成立，竞争优势归零。

> **2026-10-25 更新**：本风险此前假设「竞争者尚未进入」。任务 18 [A3.1] 的检索证明竞争者**已经进入**，
> 且不是大平台顺手加个功能，而是**两个专职的 Agent 垂直招聘平台**（`agenticcareers.co` 2,962 岗位 /
> 890 家公司日更；`agenticengineeringjobs.com` 200 岗位，已开放企业发布）。
> 竞争形态从「平台功能跟进」变为「同类专职平台的正面竞争」，且对手已具备供给规模与先发品牌认知。
> 与风险 3 联动：D1 的差异化点须相对这些垂直竞品计量。

**缓解策略**:
- 快速验证并占领细分市场
- 建立强大的社区粘性
- 保持产品创新速度
- **（2026-10-25 新增）** 正面竞争下不与对手争「更多岗位」，而是争**更准的匹配**与**更对的细分**
  ——D2（真实匹配数）是唯一能证明匹配的终端证据

## 验证实验设计

> 实验假设中的百分比一律引用 `validation-metrics.md` 判定阶梯，不独立定义。

### 实验 1: 着陆页价值主张测试（含 A/B）
- **目的**: 验证市场需求，并识别哪种价值主张更能驱动订阅
- **指标**: M1 着陆页邮件订阅数、M2 社媒互动率
- **A/B 变体**（此前缺失，`mvp-boundaries.md` 列入 A/B 测试却无实验设计）：
  - 变体 A（功能向）: "The job board for people who build AI Agents" — 强调垂直专注
  - 变体 B（痛点向）: "Stop explaining what an AI Agent is in every interview" — 强调无需重复解释技术背景
  - 变体 C（供需向）: "Where AI Agent teams hire" — 强调企业侧招聘
- **分流方式**: 按流量 1:1:1 随机分流，样本不足时（单变体 < 100 次访问）只跑 A/B 两变体
- **假设**: 整体订阅转化率 ≥ 3%（M1 达成通过值 ≥ 50/首周）
- **⚠️ 执行前提**: 本实验需平台先具备订阅表单与 `subscribers` 表（见 `design.md`）。若采用纯静态页 + 第三方 ESP，则**无法按变体归因**，此时必须先建自建表单，否则 A/B 结论不可用

### 实验 2: 用户访谈
- **目的**: 深入了解用户需求和痛点
- **指标**: M4 强需求表达比例、M5 痛点认同度
- **假设**: M4 ≥ 60%（通过值）即需求验证；≥ 80% 为强力验证

### 实验 3: 问卷调查
- **目的**: 获取大样本的定量数据
- **指标**: M3 问卷完成率、M4 强需求表达比例、M12 价值主张认同度
- **⚠️ 定义缺口修复**：旧版假设为"70% 的受访者评分为 7 分以上（10 分制）"，但问卷中**并无 10 分制需求强度评分题项**，该假设不可测量。现统一改用 M4（问卷中"非常需要"选项的选择比例），并要求问卷必须包含该题项。

## 风险监控机制

- **每日**: 监控着陆页数据（M1）
- **每周**: 总结访谈和问卷进展，对照判定阶梯更新未达标指标清单
- **每两周**: 评估整体验证进度和四项高风险（风险 1/2/3/4）的状态
- **里程碑**: Week 5（11-23 ~ 11-29）执行 `validation-metrics.md` 的判定 Gate；Week 4（11-15 ~ 11-22）完成数据汇总与打分表，**不产生新数据**

## 关键决策点

> 本文档不独立定义阈值，以下全部引用 `validation-metrics.md` 判定阶梯的指标编号。

| 情形 | 引用指标 | 决策 |
|---|---|---|
| 需求验证失败 | M1 < 10（首周）或 S3 < 50 或 M4 < 20% | 转向，见风险 1 缓解策略 |
| 供给验证失败 | M8 = 0 家承诺 或 S2 < 2 或 M9 < 30% | 转向，见风险 2 缓解策略 |
| 差异化验证失败 | D1 = 0 个 | 转向，见风险 3 缓解策略 |
| **冷启动实现** | **D2 = 0 且 M1–M12 中 ≥ 3 项未达标** | **执行单边突破策略**，见风险 4 |

>
> **实际有效采集窗口压缩为 11-01 ~ 11-14（2 周）**——第 1 周（10-25 ~ 10-31）的三项里程碑均未达成，启动项顺延至第 2 周完成。风险监测的周节奏按此实际节奏执行。

- **第 1 周（10-25 ~ 10-31）**: 完成需求风险（风险 1）初步验证——着陆页 + 问卷上线，启动开发者访谈。**状态：三项均未达成，物料已就绪，启动项顺延至第 2 周**
