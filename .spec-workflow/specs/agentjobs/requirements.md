# AgentJobs 产品定义 - 30 天市场验证

> **范围提示**：本文档定义的是**验证期要检验的假设**，而非承诺交付的功能集。产品是否进入开发，以 `validation-metrics.md`「判定阶梯」的结论为准；平台功能边界见 `mvp-boundaries.md`。

## 产品定位

AgentJobs 是 "The job board for people who build AI Agents"，一个专门为构建 AI Agent 的开发者、工程师和专业人士服务的求职平台。

## 产品假设 (Product Hypothesis)

**核心假设**：随着 AI Agent 领域快速发展，市场上缺乏一个专门为 AI Agent 开发者提供职业机会的专业化平台，导致：
- AI Agent 开发者难以找到匹配度高的相关职位
- 企业难以触达专业的 AI Agent 开发人才
- 通用求职平台无法满足这个垂直领域的特殊需求

## 目标用户定义 (Target Users)

### 主要用户：AI Agent 开发者
- **角色描述**：AI 工程师、Agent 开发者、自动化系统构建者、LLM 应用开发者
- **技能特征**：熟悉 LangChain、AutoGen、LLM 工具链、Python/Javascript、向量数据库等
- **需求痛点**：
  - 寻找纯 AI Agent 开发岗位（而非通用 AI/ML 岗位）
  - 希望雇主理解 Agent 技术栈和复杂性
  - 渴望加入专注 AI Agent 产品的团队
  - 关注行业发展趋势和薪酬水平

### 次要用户：招聘 AI Agent 开发者的企业（account type: `company`）
- **角色描述**：初创公司、AI 平台、传统企业 AI 团队的招聘负责人
- **需求痛点**：
  - 难以触达专业的 AI Agent 开发者群体
  - 无法精准描述 Agent 技术需求
  - 缺乏对 AI Agent 开发者市场行情的了解

## Killer Workflow (核心工作流程)

### 对 AI Agent 开发者而言：
1. **发现机会**：浏览针对 Agent 技能定制的职位列表
2. **匹配验证**：通过技能标签、技术栈、项目类型快速筛选
3. **深度了解**：查看雇主的技术架构、Agent 类型、发展愿景
4. **直接沟通**：与懂技术的企业直接交流，无需重复解释 Agent 技术概念
5. **职业成长**：通过社区功能了解行业趋势、薪酬对比

### 对企业而言：
1. **精准发布**：使用 Agent 特定的技术标签和要求发布职位
2. **定向推广**：推送给关注 Agent 领域的特定开发者群体
3. **智能匹配**：系统根据技能栈和经验推荐合适候选人
4. **高效沟通**：与已知具备 Agent 技能背景的候选人对话
5. **品牌建立**：在 Agent 开发者社区中建立雇主品牌形象

## MVP 边界定义

### 包含功能（平台 MVP 范围，验证通过后开发）
- **职位发布系统**：企业可发布基于 Agent 技能标签的职位
- **职位搜索系统**：开发者可按 Agent 技术栈搜索职位
- **基本匹配算法**：技能标签匹配（定义见下）
- **用户注册/登录**：开发者和企业账户体系
- **基础沟通功能**：站内消息 + 简历投递**两者都做**
- **反馈机制**：双向评价系统（最低优先级，可裁剪）

> **歧义已消除**：旧版写作"站内消息**或**简历投递"，二选一从未拍板，导致 `mvp-boundaries.md` 与 `design.md` 各自只实现了其中一半（前者只做站内消息，后者只设计了投递）。现明确两者都做，且以"申请/投递"为主流程、"站内消息"为投递后的沟通渠道。裁剪顺序见 `mvp-boundaries.md`「范围裁剪顺序」。

### 「基本匹配算法」的可验证定义

旧版验收标准写"技能匹配准确率 > 80%"，但未定义准确率的计算方式与 ground truth 来源，该指标**不可测量**。现定义为两个可计算口径：

**口径一：技能标签覆盖率 (Skill Coverage) — 自动计算，覆盖全部职位**

```
coverage(job, developer) = Σ(w_i × match_i) / Σ(w_i)
```

- `w_i` = 职位要求技能 `i` 的 `importance_level` 权重（required=2, preferred=1）
- `match_i` = 1 若开发者具备该技能标签，否则 0
- 指标：**平台展示给开发者的职位的平均 coverage ≥ 0.6**
- 意义：衡量"开发者搜到的职位是否真的利用了他的技能"，无需人工标注

**口径二：人工相关性判定 (Relevance Hit Rate) — 抽样计算**

- 抽样：随机取 20 组 (职位, 搜索该职位的开发者)
- 判定：由 1 名评审依据职位要求与开发者技能档案，逐组二分判定"相关/不相关"
- 指标：`相关组数 / 20 ≥ 0.8`
- 意义：直接对应原"80% 准确率"意图

**与范围的边界**：以上两个口径均属 `mvp-boundaries.md` 明确**排除**的"智能匹配评分系统"的对立面——coverage 是**确定性标签交集计算**，不含任何评分模型、机器学习或语义匹配。若实现中引入权重学习或语义相似度，即越界至 P1。

### 不包含功能（排除范围）
- AI Agent 技术课程/培训
- 在线编码测试平台
- 复杂的薪资数据分析
- 企业内部 HR 系统集成
- 移动端 App（优先 Web 版）

## JobSpec 概念定义

**JobSpec** 是 AgentJobs 中的核心数据模型，用于描述 AI Agent 开发相关职位：

| 维度 | 取值 | 对应 `design.md` 字段 |
|---|---|---|
| **技能栈标签** | LangChain、AutoGen、BabyAGI、ReAct、ReWOO 等 | `job_required_skills` 关联表 |
| **Agent 类型** | 多智能体协作、工作流自动化、研究辅助等 | `job_postings.agent_type` |
| **技术深度** | 入门级、中级、专家级 | `job_postings.experience_required` |
| **工作环境** | 远程、现场、混合 | `job_postings.location_type`（**唯一来源**） |
| **工作类型** | 全职、兼职、合同工 | `job_postings.employment_type` |
| **薪酬范围** | 年薪区间（根据 Agent 领域特殊性） | `job_postings.salary_min` / `salary_max` |
| **团队规模** | 创业公司、中小团队、大厂 Agent Lab | `job_postings.team_size` |

> **字段对齐修复**：旧版 JobSpec 定义了 6 个维度，但 `design.md` 的 `job_postings` 表缺少 **Agent 类型**、**团队规模**、**工作类型** 三个字段，且同时存在语义重叠的 `location_type`（远程/现场/混合）与 `remote_friendly`（是否远程友好）两列。现补齐缺失字段并删除冗余列，映射关系见上表。

## 验收标准

> **窗口区分**：30 天窗口内只有验证期，**平台尚不存在**，因此本节区分「验证期验收」（30 天内可测）与「平台验收」（开发期交付后测）。旧版将两者混列为"第一个月"，而第一个月并无平台，导致 100 个注册、10 个企业职位发布等目标在时间上不可能达成。现已拆开。

### 验证期验收标准（第 1-4 周，全部阈值引用 `validation-metrics.md` 判定阶梯）

1. 着陆页首周邮件订阅 ≥ 50（M1 通过值）
2. 完成 ≥ 10 名开发者深度访谈（S1）
3. 完成 ≥ 5 家企业深度访谈（S2）
4. 收集 ≥ 100 份有效问卷（S3）
5. 强需求表达比例 ≥ 60%（M4 通过值）
6. 企业承诺发布职位 ≥ 20%（M8 通过值）
7. 识别出 ≥ 3 个明确差异化功能点（D1 通过值）
8. **企业职位 seeding 就绪**：M8 承诺的企业已提供**具体可发布的职位内容**（非仅口头承诺），否则平台将以空职位集上线

> 第 8 项为新增项。旧版验收标准只要求"企业愿意发布"，但冷启动风险（`risk-analysis.md` 风险 4）表明：口头承诺不构成供给，平台需在开放时已有职位。

### 平台验收标准（开发期交付后测，不在 30 天窗口内）

1. 开发者能够在 30 秒内找到符合自己技能的职位
2. 用户完成注册到投递第一份简历的时间不超过 2 分钟
3. 技能覆盖率 coverage ≥ 0.6（全部职位自动计算）
4. 人工相关性命中率 ≥ 80%（20 组抽样）
5. 企业发布的职位在 24 小时内获得至少 3 个相关候选人
6. 至少达成 1 个成功的职位匹配（面试或入职）——对应 D2
7. 用户留存率（一周内再次访问）> 30%

> 原"第一个月获取 100 个开发者注册"已移出验收标准：30 天窗口内平台不存在，注册数据无从产生。该目标并入下方「成功指标」作为平台期运营目标。

### 旧版业务目标的重定基线

| 旧版目标 | 问题 | 现定基线 |
|---|---|---|
| 第一个月 100 个开发者注册 | 30 天内平台不存在 | 平台上线后 3 个月内 100 注册；验证期替代指标为 M1 订阅数 |
| 第一个月 10 个企业职位发布 | 同上；且无投放渠道定义 | 验证期 M8 ≥ 20% 承诺 + seeding 就绪；平台期再计实际发布数 |
| 至少 1 个成功职位匹配 | 依赖平台上线，验证期不可达 | 保留为 D2，判定阶段为平台期，**但**验证期须完成 seeding 谈判以保证可达 |

## 成功指标 (Success Metrics)

### 核心指标
- **月活跃用户数 (MAU)**：AI Agent 开发者 + 企业总数
- **职位匹配成功率**：成功入职人数 / 总职位数
- **用户满意度**：NPS 评分 >= 50
- **月收入 (MRR)**：来自企业招聘服务的订阅费

### 过程指标
- **职位曝光量**：平均每个职位被查看次数
- **投递转化率**：查看职位后投递简历的比例
- **沟通响应率**：双方沟通发起后的回应比例
- **技术验证通过率**：通过技能标签匹配的成功案例

## MVP 最小可行范围

1. **用户角色**：仅支持开发者和企业两种简单角色
2. **技术栈标签**：初期支持 10-15 个最主流的 Agent 技术标签
3. **地理范围**：仅支持中国和美国两个主要市场
4. **语言支持**：界面文案 zh-CN 单语言，不引入 i18n 框架与运行时语言切换；职位描述等用户输入内容允许英文（与 `mvp-boundaries.md` i18n 边界一致）
5. **认证机制**：基于自我申报，暂不引入技术验证

> 第 4 项已消歧：旧版本文档要求"仅支持中文和英文"，而 `mvp-boundaries.md` 将"多语言支持"列入排除范围，二者字面冲突。现明确区分「UI 单语言」与「内容允许英文」。
>
> 用户角色统一为「开发者 / 企业」：旧版混用"招聘方/企业/HR"，而 `design.md` 的 `users.type` 枚举为 `developer/company`。全文统一为 developer / company。
